Purpose

This document defines how StageFlow exchanges information with external systems while preserving the independence of the core domain model.

External integrations must extend StageFlow rather than reshape it.

The Integration Layer exists to isolate vendor-specific behavior behind stable internal contracts.

⸻

Architectural Principle

StageFlow owns workflow.

External systems own their respective domains.

Examples:

External System	Owns
Pretalx	Schedule, speakers, sessions
GitHub	Repository state and configuration transport
DevCon API	Conference-specific media registration
YouTube	Video publication
Vimeo	Video publication

StageFlow synchronizes with these systems but does not become their source of truth.

⸻

Integration Philosophy

Every integration follows the same architecture:

External System
↓
Adapter
↓
Integration Context
↓
Domain Events
↓
StageFlow Core

The adapter translates.

The domain remains unchanged.

⸻

Adapter Responsibilities

Every adapter is responsible for:

* authentication
* data translation
* synchronization
* retry handling
* rate limiting
* health reporting
* error reporting

Adapters should not contain business logic.

⸻

Supported Integration Categories

Schedule Providers

Examples:

* Pretalx
* future scheduling systems

Responsibilities:

* session import
* speaker import
* schedule updates

⸻

Repository Providers

Examples:

* GitHub

Responsibilities:

* receive configuration updates
* consume schedule artifacts
* version synchronization

⸻

Conference APIs

Examples:

* DevCon API

Responsibilities:

* register completed media
* publish livestream identifiers
* publish VOD identifiers
* synchronize conference metadata

⸻

Publication Platforms

Examples:

* YouTube
* Vimeo

Responsibilities:

* publish media
* return publication identifiers
* report publication status

⸻

Synchronization Strategy

Every synchronization attempt creates a Synchronization Record.

Synchronization is append-only and fully auditable.

Retries should be automatic where appropriate.

Persistent failures should require operator review.

⸻

Domain Events

Typical integration events include:

* ScheduleImported
* ScheduleUpdated
* SessionMetadataUpdated
* PackageMetadataPublished
* PublicationRegistered
* SynchronizationSucceeded
* SynchronizationFailed

⸻

Failure Philosophy

Integration failures should never interrupt live production.

If an external system becomes unavailable:

* production continues
* editorial continues
* rendering continues
* package assembly continues

Synchronization resumes automatically when connectivity is restored or when manually retried.

⸻

Future Evolution

The Integration Layer should allow additional providers to be added without requiring changes to the core domain model or bounded contexts.

New integrations should be implemented by adding new adapters rather than modifying existing production logic.
