Purpose

This document defines the major bounded contexts within StageFlow.

A bounded context is a clear area of responsibility within the platform. Each context owns specific domain objects, business rules, workflows, and terminology.

The purpose of this document is to prevent StageFlow from becoming a single tangled application where every subsystem knows too much about every other subsystem.

⸻

Design Philosophy

StageFlow should be built as one coherent platform with clearly separated internal domains.

For V1, StageFlow should remain a modular monolith, not a distributed microservices architecture.

This means:

* one deployable backend application
* one database
* clear internal module boundaries
* event-driven communication between contexts
* ability to extract contexts later if scale requires it

⸻

Primary Bounded Contexts

StageFlow is divided into eight primary bounded contexts:

1. Identity & Access
2. Event Management
3. Production
4. Editorial
5. Media Rendering
6. Packaging & Delivery
7. Publishing & Analytics
8. Integration
9. Simulation

⸻

Context Map

Identity & Access
        ↓
Event Management
        ↓
Production
        ↓
Editorial
        ↓

Integration communicates with all operational contexts through adapters and domain events.

Simulation may interact with every context in an isolated execution environment.

1. Identity & Access Context

Purpose

Manages users, roles, permissions, authentication, and access boundaries.

Owns

* User
* Role
* Permission
* Organization membership
* Event assignment
* Stage assignment

Responsibilities

* authenticate users
* authorize actions
* assign roles
* scope access by Organization, Event, Stage, or Session
* record identity-related Activity

Must Not Own

* editorial decisions
* media files
* render jobs
* delivery package contents
* event analytics

Key Rules

* Users may have different roles in different Events.
* Permissions should be explicit.
* All meaningful user actions should be attributable to a User.
* Service accounts should be distinguishable from human users.

⸻

2. Event Management Context

Purpose

Defines the planned structure of an Event.

This is the source of truth for schedule, stages, speakers, sessions, event metadata, branding configuration, and editorial configuration.

Owns

* Organization
* Event
* Stage
* Session metadata
* Speaker
* Editorial Brief
* Brand package
* Export preset definitions

Responsibilities

* create and configure Events
* import schedules
* import Speaker metadata
* define Stages
* assign Sessions to Stages
* maintain Editorial Brief versions
* configure event-level defaults
* define package and export requirements

Must Not Own

* live Media Chunk processing
* transcription jobs
* reviewer decisions
* render outputs
* delivery links
* publication analytics

Key Rules

* Devcon is an Event, not a hardcoded product mode.
* Event setup must be white-label.
* Editorial Briefs are versioned.
* Active Editorial Brief changes must be deliberate.

⸻

3. Production Context

Purpose

Manages real-time event ingest, timeline construction, transcription, system status, activities, and production health.

This context represents the live operational heartbeat of StageFlow.

Owns

* Media Chunk
* Timeline Segment
* Session Timeline
* Session Transcript
* Transcript Segment
* Activity
* Job
* Worker status
* Stage health
* Session production status

Responsibilities

* watch ingest folders
* detect complete Media Chunks
* validate Media Chunks
* create Timeline Segments
* maintain virtual Session Timelines
* transcribe new media
* stitch transcript segments
* emit live transcript updates
* maintain Activity feed
* monitor processing health
* retry failed Jobs

Must Not Own

* editorial approval
* clip metadata decisions
* final package verification
* delivery links
* publication metrics
* event strategy

Key Rules

* Media Chunks are storage objects, not editorial objects.
* Session Timelines are virtual and continuous.
* Production must continue under degraded network conditions.
* Production should emit Activities for meaningful changes.
* Production should not block Editorial when partial transcript data is usable.

⸻

4. Editorial Context

Purpose

Manages Candidate Moment discovery, review, approval, rejection, revision, tiers, Hot Moment flags, and human editorial decisions.

This context represents the human-AI editorial collaboration layer.

Owns

* Candidate Moment
* Clip
* Review state
* Editorial tier
* Hot Moment flag
* Clip metadata
* Reviewer assignment
* Review queue

Responsibilities

* analyze transcript windows for Candidate Moments
* apply Editorial Brief guidance
* assign visible tiers
* flag Hot Moments
* route Candidates to reviewer queues
* allow manual Candidate creation from transcript
* support human approval/rejection/revision
* convert approved Candidate Moments into Clips
* preserve review history

Must Not Own

* raw media storage
* transcription
* rendering implementation
* delivery links
* publication analytics
* user authentication

Key Rules

* Only human review can convert a Candidate Moment into a Clip.
* Hot Moment is an urgency flag, not a fourth tier.
* Candidate Moments reference Session Timeline timestamps, not Media Chunk timestamps.
* Editorial learning is advisory unless human-approved.
* Review workflows should optimize speed and low cognitive load.

⸻

5. Media Rendering Context

Purpose

Generates rendered media assets from approved Clips and Sessions.

Owns

* Export
* Render configuration
* Render status
* Caption rendering
* Format-specific outputs
* FFmpeg execution policy

Responsibilities

* render approved Clips
* render full Session videos
* generate vertical, square, and landscape formats
* apply optional title card or music sting
* apply captions if configured
* handle Clips crossing Media Chunk boundaries
* retry failed renders
* provide render status to Package context

Must Not Own

* Candidate Moment approval
* package delivery
* user permissions
* event strategy
* publication performance

Key Rules

* Rendering receives Session Timeline timestamps and resolves source Media Chunks internally.
* Reviewers should not configure codec details.
* Rendering failures should retry without blocking unrelated work.
* Rendering should produce durable Export records.

⸻

6. Packaging & Delivery Context

Purpose

Builds, verifies, delivers, and archives Session Packages.

This context represents the final deliverable workflow for a Session.

Owns

* Session Package
* Package checklist
* Technical verification state
* Delivery
* Delivery link
* QR code
* Download record
* Package archive state

Responsibilities

* assemble Session Package contents
* track package completeness
* expose verification checklist
* allow Technical Director verification
* generate secure links
* generate QR codes
* track sent/viewed/downloaded delivery state
* support manual delivery
* archive package records

Must Not Own

* Clip approval
* rendering internals
* transcription
* publishing metrics
* editorial scoring

Key Rules

* A Session Package should not be delivered until verified unless explicitly overridden.
* Delivery does not delete or move archive assets.
* Delivery status is part of the Session Package lifecycle.
* Packages are permanent unless intentionally removed by an administrator.

⸻

7. Publishing & Analytics Context

Purpose

Tracks where approved Exports are published and analyzes performance after production periods.

This context supports learning without disrupting live production.

Owns

* Publication
* Publication platform
* Publication URL
* Publication status
* Publication metrics
* Editorial analysis report
* Editorial recommendation
* Engagement data

Responsibilities

* record published assets
* associate Exports with platform URLs
* track publication status
* collect or import engagement metrics
* generate day-end or post-event analysis
* suggest Editorial Brief changes
* preserve recommendation history

Must Not Own

* Clip approval
* render execution
* live candidate scoring changes without approval
* package delivery
* production health

Key Rules

* Publication is distinct from Export.
* One Export may have many Publications.
* Analytics is manually initiated.
* Analytics recommendations do not automatically modify active Editorial Briefs.
* Live production should not depend on analytics availability.

⸻

8. Integration Context

Purpose

Provides the translation boundary between StageFlow and external systems.

The Integration Context allows StageFlow to consume and publish information without coupling the core platform to vendor-specific APIs, formats, or identifiers.

Owns

* External System
* External Identifier
* Synchronization Record
* Publication Target
* Adapter configuration
* Synchronization policies
* Import history
* Export history
* Webhook processing
* Retry scheduling

Responsibilities

* synchronize schedules
* synchronize speakers
* synchronize metadata
* receive webhooks
* publish package metadata
* publish external identifiers
* monitor synchronization health
* maintain synchronization history

Must Not Own

* editorial decisions
* production state
* rendering
* authentication
* package assembly

Key Rules

Every external integration must be implemented through an adapter.

Provider-specific logic must remain inside the Integration Context.

Other bounded contexts communicate using domain events and internal models rather than vendor-specific APIs.

⸻

9. Simulation Context

Purpose

Replays events, tests workflows, trains staff, and stress-tests StageFlow without affecting live production.

Owns

* Simulation Run
* Simulation Scenario
* Synthetic Stage
* Synthetic Session
* Simulated Job failure
* Simulated ingest schedule
* Simulation report

Responsibilities

* replay historical or synthetic media
* simulate multi-stage production
* accelerate or pause event flow
* inject missing chunks
* simulate worker failures
* simulate reviewer backlog
* measure latency
* train operators and reviewers

Must Not Own

* live production state
* real delivery links
* real publications
* permanent event analytics unless explicitly exported

Key Rules

* Simulation must never corrupt live Event data.
* Simulation may reuse domain objects but must isolate state.
* Simulation should generate reports useful for testing and training.
* Simulation should support Devcon-scale rehearsal.

⸻

Cross-Context Communication

Contexts communicate through:

* domain events
* service methods
* database references
* explicit APIs

They should not directly mutate each other’s owned state.

Example:

Editorial approves Candidate Moment
        ↓
ClipCreated domain event
        ↓
Media Rendering queues Exports
        ↓
ExportCompleted domain event
        ↓
Packaging updates Session Package

Ownership Rules

Rule 1 — Each object has one owning context.

A context may reference another context’s object, but it must not own or mutate that object’s internal state.

Rule 2 — State changes should occur in the owning context.

For example:

* Editorial owns Candidate approval.
* Media Rendering owns Export status.
* Packaging & Delivery owns Package verification.
* Publishing & Analytics owns Publication metrics.

Rule 3 — Cross-context workflows use events.

Contexts react to meaningful changes rather than directly controlling each other.

Rule 4 — UI may compose data from multiple contexts.

A screen can display Session, Clip, Export, Package, and Delivery data together, but actions should route to the owning context.

⸻

Modular Monolith Implementation

For V1, bounded contexts should be implemented as internal backend modules.

Suggested backend structure:

backend/
    app/
        identity/
        events/
        production/
        editorial/
        rendering/
        packaging/
        publishing/
        simulation/
        shared/

Each module should contain its own:

* models
* schemas
* services
* repository layer
* domain events
* tests

Shared utilities should be minimal.

⸻

Anti-Patterns

Avoid:

* one giant models.py
* one giant services.py
* UI-driven business logic
* direct cross-context database mutation
* treating Media Chunks as user-facing Clips
* merging Exports and Publications
* allowing AI to bypass human review
* automatically changing Editorial Briefs from analytics
* deleting production data automatically

⸻

Design Decisions

* StageFlow V1 should be a modular monolith.
* Bounded contexts should be explicit from the start.
* Publication is distinct from Export.
* Simulation is a first-class context.
* Production and Editorial remain separate.
* Packaging and Delivery are treated as one context for V1.
* Publishing and Analytics are treated as one context for V1.
* Contexts communicate through domain events rather than direct control.

⸻

Open Questions

* Should Packaging and Delivery eventually split into separate contexts?
* Should Publishing and Analytics eventually split into separate contexts?
* Should Brand Package remain in Event Management or become its own context later?
* Should Worker orchestration be its own context or part of Production?
* Should direct social platform integrations remain inside Publishing or become separate adapters?
