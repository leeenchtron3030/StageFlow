Purpose

This document defines the architectural layers of StageFlow and the direction in which dependencies are permitted to flow.

The objective is to ensure that the core business logic of StageFlow remains independent of any specific conference, scheduling platform, publishing destination, or infrastructure technology.

Every implementation decision should preserve this separation.

⸻

Architectural Philosophy

StageFlow is built in layers.

Each layer depends only on layers beneath it.

No layer should bypass or violate the responsibilities of another layer.

The architecture is intentionally designed so that conference-specific integrations can change without requiring changes to the core production engine.

The Integration Layer exists specifically to prevent external systems from leaking into the core domain.

Dependency Rules

Dependencies must always point downward.

Example:

User Interface
↓
API
↓
Editorial Context
↓
Production Context
↓
Domain
↓
Principles

Lower layers must never depend on higher layers.

⸻

External Systems

StageFlow deliberately distinguishes between systems of record and systems of workflow.

Examples of systems of record include:

* Pretalx (schedule)
* conference identity systems
* livestream destinations
* external publishing platforms

StageFlow consumes information from these systems.

It does not replace them.

⸻

Workflow Ownership

StageFlow owns:

* live production workflow
* editorial workflow
* rendering workflow
* package assembly workflow
* delivery workflow
* operational monitoring

StageFlow does not own:

* conference scheduling
* speaker registration
* livestream platform configuration
* external publishing platforms

Those responsibilities remain with the appropriate external systems.

⸻

Adapter Philosophy

Every external integration should be implemented through an adapter.

An adapter translates between StageFlow’s internal model and an external system’s representation.

The core StageFlow domain should never contain event-specific logic such as:

* PretalxSession
* DevConUpload
* YouTubeClip

Instead, adapters translate these concepts into the internal language defined by the Domain Model.

⸻

Benefits

This layered architecture provides:

* event-agnostic deployments
* white-label capability
* simplified testing
* easier maintenance
* cleaner implementation
* safer future integrations
* long-term architectural stability

⸻

Design Decisions

* StageFlow is workflow-centric, not data-source-centric.
* External systems are integrated through adapters.
* The Domain Model remains independent of infrastructure.
* The Production engine should not require knowledge of conference-specific APIs.
* New integrations should extend the Integration Layer rather than modify core contexts.

⸻

Future Evolution

The layered architecture is intended to support future integrations without requiring changes to the core production engine.

Potential future adapters include:

* additional scheduling platforms
* DAM systems
* cloud rendering providers
* CRM platforms
* sponsor management tools
* archival systems

The architecture should evolve by extending the Integration Layer rather than increasing coupling elsewhere.
