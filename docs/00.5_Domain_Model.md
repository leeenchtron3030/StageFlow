Purpose

This document defines the core domain model of StageFlow.

The domain model describes the real-world concepts StageFlow represents, how those concepts relate to each other, how they change over time, and which system responsibilities belong to each object.

This document is intentionally not a database schema. It defines the business and operational reality first. The database, API, workers, and UI should implement this model rather than redefine it.

⸻

Domain Philosophy

StageFlow is built around one central idea:

A live event is not a collection of files. It is a collection of Sessions that continuously produce media, editorial decisions, deliverables, and operational history.

The system should therefore model the world in terms of Events, Stages, Sessions, Speakers, Timelines, Candidate Moments, Clips, Packages, Delivery, and Activity.

## AR-2.0 Clarifying Note

AR-2.0 establishes StageFlow as an observational intelligence system for live event media.

This document still contains older Session-centric language that remains useful for editorial and package workflows. AR-2.0 clarifies that Production now begins with observational ingress: recorded media and supporting production signals become Production Events, then Observations, then reasoning artifacts.

Full realignment of every legacy Session-centric object is deferred to a later Architecture Release.

Observational Intelligence Concepts

Production Event

A Production Event is the universal ingress language for runtime information entering StageFlow.

It says that something happened according to a source. It does not determine what that event means.

Adapter

An Adapter is a backend contract that reports source activity as Production Events.

Adapters emit Production Events only. They do not create Observations, Evidence, Hypotheses, Findings, Verification Decisions, or Operational Products.

Dispatcher

A Dispatcher routes Production Events to matching Interpreters.

It does not interpret events or create Observations directly.

Interpreter

An Interpreter translates supported Production Events into Observations.

It begins the reasoning pipeline but does not create Evidence, Hypotheses, Findings, Verification Decisions, or Operational Products.

Scheduled Activity

A Scheduled Activity represents planned intent from a schedule source.

The planned world describes what should happen. The observed world describes what appears to have happened. Schedule data enriches reasoning but does not prove production reality.

Operator Input

Operator input is information intentionally supplied by a human operator.

Human input is another source of observable information, not privileged truth. It becomes Production Events and participates in reasoning like every other source.

Operational Product

An Operational Product is a downstream output of verified reasoning.

Operational Products must remain traceable to Observations, Evidence, Hypotheses, Findings, and Verification Decisions.

Organization

Definition

An Organization is the top-level owner of Events, users, branding, and reusable configuration.

Owns

* Events
* Users
* Brand assets
* Default export presets
* Default permission policies

Lifecycle

Created
Active
Archived

Organizations are rarely deleted.

Notes

StageFlow must support multiple Organizations without hardcoding any event-specific behavior.

Event

Definition

An Event is a scheduled production managed by StageFlow.

Examples:

* Devcon Mumbai 2026
* ETHDenver
* Literary Festival 2027

Owns

* Stages
* Sessions
* Speakers
* Editorial Briefs
* Event assets
* Event schedule
* Event-level Activity
* Event-level analytics

Lifecycle

Draft
Configured
Ready for Production
Live
Paused
Completed
Archived

Responsibilities

The Event defines the operational context in which StageFlow runs.

It answers:

* What is happening?
* Where is it happening?
* When is it happening?
* Which Stages exist?
* Which Sessions are scheduled?
* Which Speakers are involved?
* What editorial priorities apply?

Invariants

An Event must belong to exactly one Organization.

A live Event must have at least one Stage.

Stage

Definition

A Stage is a physical or virtual production source.

Each Stage corresponds to one stream of live media, usually produced by a dedicated vMix machine.

Owns

* Sessions occurring on that Stage
* Ingest configuration
* Assigned reviewers
* Stage-level health status
* Stage-level Activity

Lifecycle

Configured
Ready
Live
Paused
Offline
Completed
Archived

Responsibilities

A Stage maps incoming Media Chunks to the correct Session Timeline.

It answers:

* Which ingest source belongs to this Stage?
* Which Session is currently active?
* Are Media Chunks arriving correctly?
* Who is responsible for reviewing this Stage?

Invariants

A Stage belongs to exactly one Event.

A Stage may have only one active Session at a time.

Session

Definition

A Session is the primary editorial object in StageFlow.

A Session represents one continuous scheduled presentation, panel, performance, ceremony, or interview.

Owns

* Session Timeline
* Media Chunks
* Session Transcript
* Candidate Moments
* Clips
* Exports
* Session Package
* Delivery
* Session-level Activity

Lifecycle

Scheduled
Ready
Live
Ending
Completed
Package Building
Package Ready
Delivered
Archived

Responsibilities

The Session is the central unit of production.

It answers:

* Who is speaking?
* What is the Session about?
* Which Stage is producing it?
* What media belongs to it?
* What transcript belongs to it?
* Which Candidate Moments were identified?
* Which Clips were approved?
* Is the Session Package complete?
* Has the package been delivered?

Invariants

A Session belongs to exactly one Stage.

A Session belongs to exactly one Event through its Stage.

A Session may have one or more Speakers.

A Session should have exactly one Session Timeline.

A Session should have exactly one Session Package.

Notes

Most UI, API, and worker behavior should be Session-centric.

Session Timeline

Definition

A Session Timeline is the continuous editorial representation of a Session.

It hides the underlying Media Chunk structure from editorial workflows.

Owns

* Timeline Segments
* Continuous timestamp mapping
* Reference to source Media Chunks

Lifecycle

Initialized
Growing
Closed
Archived

Responsibilities

The Session Timeline makes the Session appear continuous even though the source media is stored in chunks.

It answers:

* What media exists for this Session?
* What time range is currently available?
* How do editorial timestamps map to source files?
* Which source chunks are needed to render a Clip?

Invariants

A Session Timeline belongs to exactly one Session.

Timeline Segments must be ordered.

Timeline time must be monotonic.

Notes

The Session Timeline is virtual. It is not a stitched video file.

## Timeline Window Candidate

### Definition

A Timeline Window Candidate represents a proposed media range within a Recording Block.

It is a timeline artifact rather than an operational product.

### Responsibilities

A Timeline Window Candidate answers:

- Where is this potential segment located?
- What time range does it occupy?

It does not determine:

- whether the range is a session
- whether it should become a clip
- whether it should become an alert
- whether it should become any operational product

### Invariants

Timeline Window Candidates exist before Findings.

Timeline Window Candidates are provider-agnostic.

Timeline Window Candidates are not persisted unless a future implementation requires persistence.

Media Chunk

Definition

A Media Chunk is a recorded media file produced by a stage recording system.

For Devcon-style workflows, Media Chunks are expected to be approximately 60 seconds long.

Owned By

* Stage
* Session
* Session Timeline

Lifecycle

Detected
Stabilizing
Validated
Registered
Processing
Processed
Failed
Archived

Responsibilities

A Media Chunk provides source material for transcription and rendering.

Invariants

A Media Chunk must reference its source path.

A Media Chunk must eventually map to a Timeline Segment or be flagged as unusable.

Media Chunks are not user-facing editorial objects.

⸻

Timeline Segment

Definition

A Timeline Segment is an indexed portion of a Session Timeline created from one or more Media Chunks.

Owns

* Timeline start
* Timeline end
* Source Media Chunk reference
* Transcript Segment reference
* Processing status

Lifecycle

Created
Transcribing
Transcript Available
Analyzed
Archived

Responsibilities

Timeline Segments bridge storage and editorial continuity.

They allow StageFlow to analyze and render across chunk boundaries without exposing those boundaries to users.

Invariants

A Timeline Segment belongs to exactly one Session Timeline.

A Timeline Segment references at least one Media Chunk.

Timeline Segments must not overlap unless explicitly marked as retry or correction data.

Session Transcript

Definition

The Session Transcript is the complete, continuously growing transcript for a Session.

Owns

* Transcript Segments
* Word-level or phrase-level timestamps
* Optional speaker diarization
* Revision history

Lifecycle

Growing

Archived

Responsibilities

The Session Transcript is the primary source for editorial analysis.

It answers:

* What was said?
* When was it said?
* Which text corresponds to which timeline range?
* What text should be displayed to reviewers?

Invariants

A Session Transcript belongs to exactly one Session.

A completed Session should have one canonical Session Transcript.

Candidate Moment

Definition

A Candidate Moment is a proposed editorial highlight.

It may be generated automatically by the Editorial Intelligence Service or manually by a reviewer from the live transcript.

A Candidate Moment is not yet a Clip.

Owns

* Suggested end time
* Moment envelope
* Transcript excerpt
* Editorial tier

* Suggested metadata

Lifecycle

In Review

Responsibilities

Candidate Moments represent editorial opportunities.

They answer:

* What might be worth clipping?
* Why is this moment being surfaced?
* How urgent is it?
* Has a reviewer made a decision?

Invariants

A Candidate Moment belongs to exactly one Session.

A Candidate Moment references the Session Timeline, not raw Media Chunks.

Only approved Candidate Moments become Clips.

## Finding

### Definition

A Finding is a human-reviewable domain object representing something StageFlow has identified as potentially meaningful.

Findings are produced after observations, evidence, and hypotheses have been organized into a coherent possible conclusion.

### May Represent

- possible session boundary
- possible editorial moment
- possible technical incident
- possible schedule conflict
- possible metadata event
- possible alert condition

### Responsibilities

A Finding answers:

- What has StageFlow found?
- Why does StageFlow believe it matters?
- What observations, evidence, and hypotheses support it?
- What review or verification may be required?

### Invariants

A Finding must be traceable to supporting reasoning artifacts.

A Finding is not automatically verified.

A Finding must not directly create operational products without verification.

⸻

## Verification Decision

### Definition

A Verification Decision records immutable judgment about a Finding.

Verification Decisions do not modify Findings.

Instead, they append review history.

### Responsibilities

A Verification Decision answers:

- What judgment was recorded?
- Why?
- Who recorded it?
- When?
- Were adjustments suggested?

### Invariants

Verification Decisions are append-only.

Verification Decisions reference Findings by identifier.

Verification Decisions do not create operational products.

Operational products are created only by downstream processes after verification.

External Identifier

Definition

An External Identifier maps an internal StageFlow object to the identifier used by an External System.

Examples include:

* Pretalx Session ID
* Pretalx Speaker ID
* GitHub Commit SHA
* DevCon Session ID
* YouTube Video ID

Owns

* External System reference
* Internal object reference
* External identifier value
* Identifier type
* Creation timestamp

Responsibilities

Allows StageFlow to correlate internal domain objects with external systems without introducing provider-specific fields into the core domain.

Invariants

A StageFlow object may possess multiple External Identifiers.

Each External Identifier belongs to exactly one External System.

Ownership Rules

Session Ownership

The Session owns most production objects.

If uncertain where a production object belongs, default to the Session unless there is a strong reason otherwise.

Event Ownership

The Event owns scheduling, editorial context, branding context, and analytics.

Organization Ownership

The Organization owns durable configuration, users, assets, and default settings.

⸻

Boundary Rules

Editorial Boundary

Candidate Moments and Clips operate on Session Timeline timestamps, not Media Chunk timestamps.

Storage Boundary

Media Chunks are storage artifacts.

They should not be exposed as primary UI objects.

Review Boundary

Only human review can convert a Candidate Moment into a Clip.

Delivery Boundary

Only verified Session Packages can be delivered.

Learning Boundary

Editorial learning does not automatically modify an active Editorial Brief.

Design Decisions

* StageFlow is Session-centric.
* Media Chunks are not editorial units.
* Candidate Moments are distinct from Clips.
* Hot Moment is an urgency flag, not a fourth tier.
* Session Packages are first-class domain objects.
* Delivery is part of the Session Package lifecycle.
* Activities are append-only records of meaningful system behavior.
* Editorial Briefs are versioned and human-controlled.
* Most production behavior should be event-driven.

Open Questions

* Should a Session be allowed to have multiple simultaneous active Speakers?
* Should Panels use the same Session model or introduce a Panel subtype later?
* Should Delivery support multiple recipients per Session Package in V1?
* Should published social URLs be modeled as part of Export, Clip, or a separate Publishing object?
* Should Session Package verification allow partial delivery under degraded conditions?
